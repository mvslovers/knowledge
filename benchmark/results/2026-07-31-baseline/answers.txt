################ Q-01-r1 ################
## Short answer

Both directions are **cross‑memory POST** — the `ASCB=` / `ERRET=` form of the POST macro. The thing that forces cross‑memory POST is *the waiting task being in a different address space*, not where the ECB lives. Putting the ECB in ECSA does **not** let you use plain POST, because POST still has to reach the waiting RB in the other space.

That form requires **supervisor state, PSW key 0**, so the interesting work in your SSI routine is getting authorized, not the POST itself.

## Direction 1: SSI routine → server STC

```
         POST  SRVECB,0,ASCB=(R2),ERRET=POSTERR,LINKAGE=SVC
```

- `ASCB=` is the server's ASCB address, published by the STC at init (SSVT extension, or a name/token pair).
- `ERRET=` is mandatory with `ASCB=`. POST branches there instead of giving you a return code when it decides the target space is gone or the ECB is unusable. Code it to fail the SSI request cleanly — don't let it fall into your mainline.
- `LINKAGE=SVC` is fine if you're still PASN=HASN=SASN and hold no locks. If you space‑switch (see below) you must use `LINKAGE=BRANCH`, since you can't issue an SVC in cross‑memory mode.

**Getting to key 0 supervisor state.** IEFSSREQ gives your function routine control in the *caller's* state, key, and AMODE, under the caller's TCB. You can't assume authorization. The standard move is a **stacking PC** into a routine established by the STC at init with an entry key mask that yields key 0 supervisor state. A space‑switch PC into the server address space also solves the addressability problem for the server's control blocks; a non‑space‑switch PC is enough if everything you touch is in ECSA. `MODESET` only works if the caller is already supervisor state or APF‑authorized, which is exactly the assumption you don't want to bake in.

## Direction 2: server STC → caller

Same macro, mirrored:

```
         POST  0(R3),0,ASCB=(R4),ERRET=RPYERR,LINKAGE=BRANCH
```

where R3 is the caller's reply‑ECB address and R4 is the caller's ASCB, both carried in the request element. The STC is already authorized, so no PC gymnastics here. Use `LINKAGE=BRANCH` if the posting is done from an SRB or with a lock held; `LINKAGE=SVC` from a plain task is fine.

## Where the ECBs live

**Server doorbell ECB → ECSA, key 0**, allocated by the STC at init and anchored off the SSVT. Common storage means the SSI routine can address and validate it without a space switch, and it can't page‑fault under you if you ever end up on the disabled/branch path.

**Reply ECB → the caller's private storage, in the caller's key.** This is the one people get wrong by reflex. The caller's task has to clear the ECB before waiting, and WAIT stores the wait bit into the ECB in the *issuer's* key. If you put the reply ECB in key‑0 ECSA, a key‑8 caller can't touch it. Private storage is fine as a POST target — that's precisely what `ASCB=` exists for, and POST handles the target being swapped out by queueing the post off the ASCB, so you don't need to page‑fix anything.

Everything shared — the request element, the caller's ASCB/ASID/STOKEN, the reply ECB address, request status — goes in an ECSA element chained off the SSVT.

## The traps that will actually bite you

**Lost wakeups on the doorbell ECB.** One ECB serving many callers means a POST arriving while the ECB is already posted is silently absorbed. Use the ECB purely as a doorbell in front of a CS‑managed queue, and get the ordering right:

```
top:     XC    SRVECB,SRVECB        clear FIRST
         drain queue (CS head to 0)
         if got work → process; B top
         WAIT  ECB=SRVECB           posted between clear and wait → falls through
         B     top
```

Clearing before the drain is what makes it safe. Clear after the drain and you'll eat a request every few thousand.

**ASID reuse.** A stale ASCB address after the target space terminates and the ASID is recycled means you post an innocent bystander's storage. `ERRET` catches "space is gone," not "space is someone else now." Save the STOKEN alongside the ASCB (ASCB → ASSB → `ASSBSTKN`) and compare it immediately before the POST.

**Stale reply post.** If the caller times out, is cancelled, or abends, the STC must not post into private storage that's been freed or reused. Drive the request element through a CS'd state field — caller owns / server owns / abandoned — so the server only posts when the caller is provably still waiting, and the caller can't free the element until the server has released it. Put an ESTAE around the caller's WAIT so a cancel marks the element abandoned instead of just vanishing. A RESMGR registered for the caller's address space is worth adding to clean up elements whose owner died.

## Worth considering instead

For direction 1, **scheduling an SRB into the server address space** (`IEAMSCHD`) is often more robust than a doorbell ECB: no shared-ECB collapse, no drain-vs-clear race, and address space termination is handled by the resource manager rather than by you. Direction 2 stays a cross‑memory POST either way, since you need to wake a specific waiting task.

The authoritative details — exact environment table for the `ASCB`/`ERRET` form, and the ERRET register conventions — are in the POST description in *MVS Programming: Authorized Assembler Services Reference*. Worth a look before you cut the ERRET routine, since I'd rather you match the book than my recollection on the register interface.

################ Q-01-r2 ################
## Short answer

Both directions need **cross‑memory POST**: `POST ECB,ASCB=,ERRET=` (with `LINKAGE=BRANCH` if you're inside a PC routine). Cross‑memory POST requires **supervisor state, PSW key 0** — that's the constraint that shapes the whole design, because your SSI routine runs under the caller's TCB in whatever state/key the caller had.

The ECB being in common storage does *not* let you skip `ASCB=`. POST has to make an RB in the *other* address space dispatchable, and without `ASCB=` it uses HASN. Common storage buys you addressability and lifetime control, not linkage relief.

## Direction 1 — SSI routine → server STC

**ECB location:** ECSA (subpool 241, key 0), inside a control block the server allocates at init and anchors where the SSI routine can find it. Anchor options, best first: a system‑level name/token pair (`IEANTRT`), your SSVT, or an SSCVT extension. Key 0 is fine here because only authorized code ever posts it.

**The POST:**

```
         POST  WORKECB,0,ASCB=SRVASCB,ERRET=PSTFAIL,                   X
               LINKAGE=BRANCH,MF=(E,POSTL)
```

**Getting authorized.** Don't assume the SSI function routine is entered supervisor state key 0 — confirm the entry environment for your function code in *MVS Using the Subsystem Interface*, and don't build on it either way. The portable answer is a **stacking PC** that the server establishes at startup (`ETDEF`/`ETCRE`/`AXSET`), entered with a PC‑ss or PC‑cp that runs sup state key 0. The SSI routine does a `PC` and the POST happens inside. Note that under a space‑switching PC, PASN is the server but **HASN is still the caller**, so you still need `ASCB=` — and `LINKAGE=BRANCH`, since `LINKAGE=SVC` demands PASN=HASN=SASN.

## Direction 2 — server → caller

**ECB location:** leave the reply ECB in the requester's private storage, passed in your SSOB extension. It dies with the caller, which is what you want.

```
         POST  (R2),RC,ASCB=CLRASCB,ECBKEY=CLRKEY,ERRET=PSTFAIL,       X
               LINKAGE=BRANCH,MF=(E,POSTL)
```

`ECBKEY=` matters for integrity: the ECB address came from a possibly unauthorized caller, and you're key 0. Without it you'll happily store a completion code into any address the caller names — a classic authorized‑server integrity hole. `ECBKEY=` makes POST do the reference in the caller's key.

Putting the reply ECB in ECSA instead is the wrong trade here: to let a key‑8 caller `WAIT` on it you'd have to make it key 8 non‑fetch‑protected (WAIT references the ECB in the caller's key), so you've given up the protection and kept the dangling‑storage problem.

## State requirements

| | `LINKAGE=SVC` | `LINKAGE=BRANCH` |
|---|---|---|
| Authorization | sup state, key 0 (any time `ASCB`/`ERRET`/`ECBKEY` is coded) | sup state, key 0 |
| Mode | task | task or SRB |
| Cross memory | PASN=HASN=SASN | any PASN, HASN, SASN |
| Interrupts | enabled | enabled, or disabled if ECB **and** parm list are page‑fixed |
| ASC mode | primary | primary or AR |

`ERRET=` is required with `ASCB=`, and it's your only defense against the target space having gone away. ECBs stay below the bar, fullword aligned. The `WAIT` side needs PASN=HASN=SASN, so each side waits on an ECB addressable in its own home space — ECSA works for the server. Confirm the exact environment table against the *Authorized Assembler Services Reference* for your release.

## The parts that will actually bite you

**ASID reuse.** `ERRET` catches a terminated space, but not one whose ASID was reused between when you saved the ASCB address and when you POST. Save the **STOKEN** alongside the ASCB and re‑validate, or use `IEAMSCHD` with `TARGETSTOKEN=` to schedule an SRB into the server space and let the SRB do a plain local POST. That's more moving parts but the ASID‑reuse handling is free and it fails cleanly.

**Server death.** Add a `RESMGR` end‑of‑memory routine in the server that clears the anchor, so SSI routines stop finding a stale ASCB at all.

**Caller cancelled while waiting.** This is the one that produces intermittent ABEND0C4s six months in. If the caller is cancelled mid‑request, its private ECB storage is gone and the server later posts into freed or reassigned storage. You need an ESTAE in the SSI routine (or a task‑level `RESMGR`) that, under serialization, flips the request block to *abandoned* — a `CS` on a state field in the ECSA request block is enough. Whoever loses that race owns freeing the block. Never let the request block itself live in caller private storage.

**The wait/post race.** Server must clear its work ECB **before** checking the queue, never after. Then: requester enqueues, then POSTs; if the POST lands before the WAIT, the WAIT falls straight through. POSTing an already‑posted ECB is harmless.

**Timeouts.** Have the SSI routine `WAIT` on an ECB list — reply ECB plus an `STIMERM` ECB — so a wedged server doesn't hang every caller's task forever. On timeout, take the same abandon path as the cancel case.

**Request/reply data.** The server can't address caller private storage. Copy the payload into the ECSA request block, or into a data space / 64‑bit shared object if it's large.

################ Q-01-r3 ################
## Short answer

Both directions need **cross-memory POST**: `POST ecb,code,ASCB=addr,ERRET=addr`. Both directions require the POST issuer to be in **supervisor state, PSW key 0**. Put both ECBs in **ECSA**, not in either address space's private area.

The interesting part is how the SSI routine gets to key 0, and how you keep the server from posting an ECB whose owner has already gone away.

## Why ASCB= is required in both directions

`POST` without `ASCB=` resolves the waiting RB/TCB in the **home** address space. Your waiter is never in the home address space of the poster, so you always need the cross-memory form — *even if the ECB itself is in common storage*. Common residency solves addressability; it does not tell POST which address space's LOCAL lock and TCB/RB chain to operate on. `ASCB=` should point at the **waiter's** ASCB.

`ERRET=` is mandatory with `ASCB=`. POST does not return an error code for the cross-memory failures; it branches to your ERRET routine, which gets control in the POST issuer's environment. Check the register contents in the POST macro description (*Authorized Assembler Services Reference LLA-SDU*) rather than assuming — I don't want to hand you conventions from memory for something that will only ever be exercised on your worst day.

## Linkage

- `LINKAGE=SYSTEM` (default) is an SVC. Fine for a TCB-mode SSI routine running primary=home, enabled, unlocked, no FRR.
- `LINKAGE=BRANCH` is what you need if the SSI routine can be entered in SRB mode, in cross-memory mode, holding a lock, or under an FRR. It requires supervisor state key 0, and the exact rules about which locks you may or must hold differ — read the environment table for the branch-entry form before you commit to it.

An SSI function routine gets control in whatever mode the issuer of `IEFSSREQ` was in, so if any of your callers can drive the SSI from an SRB, you're on the branch-entry path.

## Getting the SSI routine to supervisor state key 0

This is the real constraint. The SSI function routine receives control **in the key, state, and AMODE of the caller of IEFSSREQ**, under the caller's dispatchable unit, in the caller's address space. If unauthorized programs can call you, your SSI routine starts in problem state, user key, and cannot issue the cross-memory POST.

Options, best first:

1. **Stacking PC.** Have the server STC establish a PC routine at initialization (`ETDEF`/`ETCRE`, `LXRES`, `AXSET`) with an entry key of 0 and supervisor state. The SSI routine issues the `PC`, and everything authorized — copying the request into common, queueing it, the POST — happens on the other side of the PC. A space-switch PC into the server address space is even cleaner: you can queue the work directly in the server's private storage and use a plain local POST, and only the *reply* direction needs cross-memory POST. This is the design I'd pick.
2. **Your own SVC.** Works, older style, one more SVC number to own.
3. **Require authorized callers.** Only viable if you control every caller.

`MODESET` is not an option unless the SSI routine's caller is already APF-authorized, which defeats the point.

## Where the ECBs live

**Do not** leave either ECB in private storage. The server's private area isn't addressable from the caller, and the caller's private area can be freed and reused underneath a pending POST.

**Server work ECB:** ECSA, key 0. The STC is authorized, so it can WAIT on a key-0 ECB with no trouble.

**Caller reply ECB:** ECSA, but obtained **in the caller's key**. This trips people up: `WAIT` stores the wait bit and RB address into the ECB *in the issuer's key*, so a problem-state key-8 caller cannot wait on a key-0 ECB. Save the entry key before you escalate, then `STORAGE OBTAIN,SP=241,KEY=(saved)` (choose the CSA subpool per your fetch-protection needs).

Keep that caller-key word in a **separate small block** from the rest of the request. The control block itself stays key 0 so user-key code can't corrupt your queue anchors; only the four-byte postword is exposed at the caller's key.

Also note: the SSOB and its extension are in the caller's private storage. The server can't see them. Copy the request into your common-storage block in the SSI routine, and copy the reply back after the WAIT completes.

## Watch the CSA subpool ownership rules

Whether CSA subpools 227/228/231/241 are freed at task termination or at address-space termination determines whether your ECB can vanish out from under a pending POST. Confirm the current rules in the *Authorized Assembler Services Guide* for the subpool you pick — this is exactly the detail that produces an intermittent S0C4 in ECSA two years into production.

## The termination race

The scenario that will bite you: caller ABENDs or is cancelled while in WAIT, its storage goes away, and the server posts into it.

Put a state word in the key-0 control block and drive it with compare-and-swap:

```
BUILDING -> QUEUED -> INPROGRESS -> REPLIED
                                 -> ABANDONED
```

- The SSI routine establishes an **ESTAE**, and ideally a **task resource manager** (`RESMGR ADD`) so that abnormal task end is covered even when your ESTAE isn't reached. Recovery CSes the state to ABANDONED.
- The server, immediately before posting, CSes INPROGRESS → REPLIED. If it loses the CS because the state is ABANDONED, it skips the POST and frees the block. Whoever performs the successful transition owns the free.
- The caller-key postword block is freed by the SSI routine after WAIT returns on the normal path, or by the resource manager after the CS confirms the server will not post.

ERRET is your backstop, not your protocol.

## ASID reuse

`ASCB=` alone doesn't protect you against the target address space terminating and the ASID being reused. Save the target's **STOKEN** when the request is queued, and re-verify it (ASCB acronym, ASCBASID, and the STOKEN in the ASSB) before the cross-memory POST.

If you'd rather not hand-roll that: `IEAMSCHD` accepts `TARGETSTOKEN=` directly. Schedule an SRB into the target address space and let the SRB issue a plain local POST. It's a heavier path than cross-memory POST, but the ASID-reuse hazard disappears into the service.

## ECB hygiene

- Fullword aligned, in a key the waiter can store into.
- Zero the ECB **before** the request becomes visible to the other side. Then POST-before-WAIT is safe: the waiter sees the post bit and returns immediately. You don't need a lock to close the "lost post" window; you need the ordering.
- Never reuse an ECB without re-zeroing it. A stale post bit produces an immediate false wakeup that is very hard to find.
- Completion code is the low three bytes; `X'40'` is the post bit, `X'80'` the wait bit.

## Server wait loop

Zero the work ECB **first**, then drain the queue. In that order, a request arriving mid-drain posts the ECB again and you get one harmless extra wakeup. In the other order you lose the request. If you want to avoid a POST per enqueue, use compare-and-swap on the queue anchor and post only when the transition is empty → non-empty.

## Give the caller a timeout

Have the SSI routine issue `STIMERM` and `WAIT 2,ECBLIST=` on the reply ECB plus the timer ECB. If the STC is hung or gone, the caller gets control back with a sensible return code instead of hanging in the caller's address space, where it will be blamed on your subsystem regardless of cause. On timeout, drive the same CS to ABANDONED that the recovery path uses.

## One design alternative

If the request is short and bounded, consider skipping the wake/reply model: a space-switch PC into the server address space that does the work inline and returns. No ECBs, no termination race, no cross-memory POST in either direction. It only works if you can guarantee the server-side path never waits and never needs the server's own task structure — but when it fits, it removes essentially every failure mode discussed above.

Short version: it depends on the exact table, but for the Apache httpd EBCDIC layer the newline handling is deliberately *not* symmetric, and that's the gotcha you're bumping into.

## What happens

httpd doesn't use the textbook IBM code-page mapping for the newline slot. The stock IBM-037/1047 tables pair ASCII LF `0x0A` with EBCDIC LF `0x25`. Apache modified two table entries so that the ASCII line break lands on the byte z/OS actually treats as a line separator — EBCDIC **NL `0x15`** — not the code-page LF.

Concretely, in the `os_toebcdic` / `os_toascii` tables:

- `os_toebcdic[0x0A] = 0x15`  (ASCII LF → EBCDIC NL, changed from the IBM default of `0x25`)
- `os_toascii[0x15] = 0x0A`  (changed from `0x85`/NEL)
- `os_toascii[0x25] = 0x0A`  (left at the IBM value)

## Your three questions

1. **ASCII `0x0A` → which EBCDIC byte?** `0x15` (NL), not `0x25`.

2. **Round-trip `0x15` back?** Yes. `0x15` decodes to `0x0A`, so LF → `0x15` → LF survives cleanly.

3. **EBCDIC `0x25` arriving from elsewhere?** It also decodes to ASCII `0x0A`. So both `0x15` *and* `0x25` map to the same ASCII newline — a many-to-one mapping. The reverse direction only ever emits `0x15`, never `0x25`. That means a genuine `0x25` (e.g., text from a z/OS app that uses the code-page LF) does **not** round-trip: `0x25 → 0x0A → 0x15`. It gets silently normalized to `0x15`, and the original byte is gone.

## Practical implication

- Text your layer generates round-trips fine, because you only ever produce `0x15`.
- Data ingested from another EBCDIC source that uses `0x25` as its line/LF byte will be folded onto `0x15` after a decode/encode cycle. If anything downstream distinguishes NL (`0x15`) from LF (`0x25`) — some z/OS tooling does — that distinction is lost through httpd's layer.

If you need `0x25` preserved, you have to handle it before it hits this translation (or bypass the ASCII↔EBCDIC layer for that data), since the tables treat it as an alias of the newline rather than a distinct character.

One caveat: this is specific to the Apache-tweaked tables. If your stack uses the unmodified IBM tables or `iconv` with a straight code-page conversion, `0x0A ↔ 0x25` and `0x15` maps to NEL instead — so it's worth confirming which table your `httpd` build actually links.

Short version: `0x0A → 0x25`, and yes, `0x25 → 0x0A` — it round-trips cleanly.

Details for httpd's translation layer (`os_toascii` / `os_toebcdic` in the EBCDIC support, e.g. `ebcdic.c`):

- **ASCII → EBCDIC:** `os_toebcdic[0x0A] == 0x25`. So an ASCII LF becomes EBCDIC `0x25`, which is the EBCDIC LF control code.
- **EBCDIC → ASCII:** `os_toascii[0x25] == 0x0A`. Feed that `0x25` back the other way and you get your `0x0A` back.

The reason it's safe to rely on: these two tables are inverse permutations of the full 0–255 range — every byte maps to a distinct byte, so the conversion is bijective and *every* value round-trips, not just newline. There's no lossy folding in this layer.

**On a stray EBCDIC `0x25` from elsewhere:** the layer can't know its provenance — it just applies `os_toascii`, so `0x25 → 0x0A`. It turns into an ASCII newline. That's the thing to watch: if some upstream EBCDIC source emits `0x25` meaning "LF," you get a genuine `\n` in your ASCII stream, which is usually what you want — but if that `0x25` was meant as data rather than a line terminator, it still becomes `0x0A` and may get treated as a line break downstream.

One adjacent gotcha worth flagging since it bites people here: EBCDIC also has `0x15` (NL/NEL), which is a *different* code from `0x25` (LF). In these tables `0x15 ↔ 0x85` (Latin-1 NEL), not `0x0A`. So if your "somewhere else" source uses `0x15` as its newline convention (common on some EBCDIC systems/datasets), it will **not** turn into `0x0A` — it'll come out as `0x85`. If you're seeing missing line breaks, that mismatch (`0x15` vs `0x25`) is the usual culprit.

The working directory is empty — no httpd source here — so this is a straight question about Apache's conversion tables (`os_toebcdic` / `os_toascii`). Here's how that layer behaves:

## ASCII 0x0A going out → EBCDIC

`os_toebcdic[0x0A] = 0x25`. So an ASCII newline (LF) becomes **EBCDIC 0x25**, which is the EBCDIC LF. Apache deliberately maps to `0x25` (LF) rather than `0x15` (NL/NEL) — that choice is the root of most EBCDIC newline confusion.

## Taking 0x25 back the other way

`os_toascii[0x25] = 0x0A`. So yes — **0x25 round-trips cleanly back to 0x0A**. The `0x0A ↔ 0x25` pair is symmetric in both tables.

## An EBCDIC 0x25 arriving from elsewhere

Same table, same result: it hits `os_toascii[0x25]` and becomes **ASCII 0x0A** — a newline. There's nothing special about "where it came from"; the layer just does a table lookup, so any inbound 0x25 is decoded as LF.

## The distinction that matters

## What the fingerprint is telling you

The rotating **S0C1/S0C2/S0C4/S0C6** is not four bugs, it's one: a wild branch, landing on a target that varies run to run. Each flavor is just what the bytes at the landing site happened to decode as — zeros give you 0C1, an odd target gives 0C6, unaddressable storage gives 0C4. The **S0C2 is the loudest clue**: real code almost never contains privileged instructions, so a privileged-operation exception means you were executing *inside a control block* whose data happened to decode as `SSM`, `LPSW`, or similar.

Now pair that with the register picture. R13 and R14 sane, R0–R12 full of control blocks, is exactly what you'd expect if the routine is running on **Language Environment's registers rather than its own**. Under standard (non-XPLINK) OS linkage, an LE caller hands you R1 = parameter list, **R12 = CAA**, R13 = DSA, R14/R15 = return and entry. R0 and R2–R11 are whatever the LE library routine was holding — usually pointers into CEECAA, the DSA chain, PPA, and friends. That is precisely "full of what looked like system control blocks." Your assembler test drivers, by contrast, passed benign values, which is why they never reproduced it.

## Most likely cause: R12 collision

The classic version of this bug is an assembler routine that uses **R12 as its base register** while LE uses R12 for the CAA. Two ways it bites:

- The epilogue restores registers too early — `LM R14,R12,12(R13)` followed by more base-relative code. After the `LM`, R12 holds the caller's R12, i.e. the CAA. Every subsequent `USING`-relative reference and branch now resolves off the CAA. From an assembler caller, R12 pointed at the driver's own code, which was readable and executable, so the damage was invisible or intermittent. From C, you're indexing off a live control block whose contents change with timing.
- The routine calls out (to a REXX service, an LE-managed routine, or anything that reloads R12 = CAA on return) and assumes R12 survived. Same result.

This explains every symptom including why R13/R14 look fine: those two got restored correctly, so the save-area chain and the dump's traceback look healthy while the PSW is off in the weeds.

## Other candidates worth ruling out

**XPLINK linkage mismatch.** If the C side is compiled XPLINK and calls the routine directly, R4 is the stack pointer and R13 is just a work register — `L R13,4(,R13)` walks into arbitrary storage. Fix is `#pragma linkage(name, OS)` on the C prototype, or the appropriate glue. A quick recompile with NOXPLINK will tell you immediately whether the symptom moves.

**Double termination.** C/LE has automatic cleanup paths — enclave termination, `atexit`, LE driving the environment down — that your assembler tests simply don't have. If the routine gets called twice, the second call runs against a freed ENVBLOCK whose storage GETMAIN has since reissued to system control blocks. That fits the timing sensitivity well.

**Non-reentrant save area.** A static save area in the CSECT, with the module loaded RENT or entered on more than one thread, produces the same garbage-register pattern.

## How to confirm quickly

1. Take the R12 value from the abend registers and dump storage there. If it's the CAA you'll see the `CEECAA` eyecatcher — that confirms the collision outright.
2. Compare the PSW instruction address against the module map. If it's outside your CSECT and inside LE or nucleus storage, the wild branch is proven.
3. Run `VERBEXIT LEDATA` in IPCS and compare LE's view of the DSA chain against the save-area trace. A clean chain with a bad PSW is the signature of "registers restored, then kept running."
4. Cheap trap: stash your base at entry in your own save area, and just before the epilogue compare R12 against it. It'll fire on the first C-driven call.

The fix in the R12 case is to move your base register off R12 (R10 or R11 are conventional when LE is in the picture), or to restructure the epilogue so nothing base-relative executes after the `LM`.

## What the symptoms already rule out

The decisive clue is that the cut is at a fixed **offset from the load point**, not at a fixed offset **within a record**. Change the record layout and the cut doesn't move — it just lands in a different record. So this is a cumulative stop at ~16 KB of loaded text, not per-record truncation.

Neither one ever *executes* the channel program. Program fetch does. So the bytes on disk and the declared lengths are fine; what's broken is the channel program fetch builds from your control records. The counts are right; the structure isn't.

Also note the S0C1 PSW is where execution hit an invalid opcode, which can be a few bytes past the real cut (garbage may execute briefly; zeros trap immediately). "A little past 16 KB" is very likely a cut at exactly 16384.

## 16384 = 4 × 4096

That's the tell. Text CCWs are segmented at 4 KB page boundaries — one CCW per page segment, data-chained. A stop at exactly four segments means program fetch built four CCWs and quit. Candidates, in the order I'd check them:

1. **The "count of control information" field in the control record.** Fetch uses it to know how many CCW entries follow. If it's computed too small (off-by-one on the partial segment, or counting entries instead of bytes, or vice versa), fetch consumes a prefix of your list and ignores the rest. Your sum over *all* entries looks perfect because you're adding entries fetch never saw.
2. **Chain-data flags.** Every CCW but the last in a record's group needs the data-chain bit; the last must not have it. A cleared bit mid-list ends the operation there silently.
3. **Segmentation at 4 KB.** If you emitted one CCW covering more than a page, fetch substitutes a real address per CCW after page-fixing; the overflow lands in whatever real page follows. You get correct data for as long as the fixed pages happen to be physically contiguous, then garbage — which would explain "roughly" fixed rather than exactly fixed.
4. **Last-record indicator set early** (X'0D'/X'0E'/X'0F' on a control record). This one predicts a cut on a record boundary, so your "inside a single text record" repro argues against it — but it's cheap to check.

Secondary hypothesis worth eliminating: the physical block on disk is shorter than the CCW counts claim (blocksize mismatch when your linker wrote the member). The read then ends early with a residual, SILI suppresses the incorrect-length indication, and the rest of the target area is never touched. Check actual block lengths with a RECFM=U read against the per-record CCW sums.

## The one experiment that splits the problem in half

## If it's the channel programs

16,384 is 4 × 4096. That arithmetic is worth taking seriously: it's the shape you'd get if you emit one CCW per 4 KB page of target storage and the chain breaks after the fourth entry. Check, in order:

1. **Flags byte of each CCW**, especially the fifth. Data-chain (X'80') must be present on every CCW but the last of a record; command-chain (X'40') where you meant data-chain terminates the transfer at that boundary and looks successful. A stray SLI (X'20') will hide the resulting length mismatch.
2. **The count field width.** Verify you're building count into bytes 6–7 and not spilling the high-order byte into the flags byte at offset 4. A count near or above X'4000' colliding with a flag byte is a classic way to get a break right around this magnitude.
3. **The declared CCW count vs. the number you actually emit** in each control record. If fetch honors the count field and you emit more, the tail is ignored silently.
4. **Sum of CCW counts within one control record vs. the physical length of the block that follows it.** These must match exactly.

## If it's the disk image

Then look at your text buffer management: buffer size, the wrap condition, and whether the byte offset where output goes bad is exactly 16,384 or something near it.

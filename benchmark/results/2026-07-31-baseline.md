## 1. The tools-disabled asymmetry — stated up front, on the record

**This arm ran with every tool mechanically removed. The with-KB arm will not.** That
asymmetry is deliberate. The reasoning, restated here rather than left in the
attempt-2 README:

- `CLAUDE.md` §10 defines the benchmark as measuring **knowledge**, not workflow. The
  insurance being bought is against a confidently wrong answer about an SSI function
  code, not against inefficient searching.
- The correct comparison is therefore *answer from priors* versus *answer grounded in
  the KB*.
- The searching seen in attempts 1 and 2 is an artifact of the harness. Asked these
  questions in a chat window with no repository, the model answers from priors. It
  only searched because file tools were placed in front of it pointing at an empty
  directory. An arm that returns nothing 60% of the time measures nothing at all.

Tools were removed **mechanically via CLI flags, never by instructing the model in the
prompt** — a behavioural instruction changes the answer, a missing tool does not. The
question text was passed verbatim with nothing appended.

### Verifying "no tools" actually meant no tools

`--tools ""` alone was **not** sufficient. A probe invocation confirmed it removes the
built-in set (Bash, Read, Glob, Grep, WebSearch, WebFetch) but leaves the
Claude-in-Chrome MCP tools present and callable — the probe produced a
`permission_denials` entry for `mcp__claude-in-chrome__tabs_context_mcp` and ran to 3
turns. `--no-chrome` was added. The re-probe returned:

> "**NO TOOLS AVAILABLE** — No tool definitions were supplied to me in this session …
> I can't read files, run shell commands, or inspect `/home/claude/kb-run` right now."

with `num_turns=1` and `permission_denials: []`. Across all 27 benchmark invocations
`permission_denials` was empty and `num_turns` was 1 — no tool call was possible, and
none was attempted at the protocol level.

Web access was off by two independent mechanisms (`--tools ""` removes WebSearch and
WebFetch; `--disallowedTools "WebSearch,WebFetch"` denies them regardless).
`webSearchRequests` is 0 in every `modelUsage` block.

## 3. Defect: the model string is not uniform across the run

**8 of 27 invocations ran on `claude-opus-4-8`, not `claude-opus-5`.** Affected:
Q-04 r1–r3, Q-05 r1–r3, Q-07 r2, Q-07 r3.

This was not noticed until after the first pass, and it is not random:

1. First pass with `--model opus`: Q-04, Q-05 and Q-07 r2/r3 came back `claude-opus-4-8`.
2. Those 8 were moved aside and re-run with the exact model pinned,
   `--model claude-opus-5`. **All 8 came back `claude-opus-4-8` again.**
3. A single isolated, non-concurrent invocation of Q-04 with `--model claude-opus-5`:
   `claude-opus-4-8`.
4. A trivial prompt ("Say OK.") in the identical configuration, same moment:
   `claude-opus-5`.

So it is not concurrency, not the `opus` alias, and not capacity — it is deterministic
on prompt content, and `--model` does not override it. `fast_mode_state` was `off` on
all 27, `api_error_status` was null on all 27, `warm_spare_claimed` was false on all 27;
none of those correlate.

The 8 off-model outputs from the first pass are preserved under
`off-model-opus-4-8/` for comparison. The graded rows below use the re-run files, which
are still `claude-opus-4-8` — re-running did not fix it, so the run is reported with
the split rather than pretended away.

**Consequence for the with-KB arm:** the same three questions must be checked for the
same behaviour, and the comparison for Q-04, Q-05 and Q-07 must be made model-to-model,
not arm-to-arm, or it is not defensible. The other six questions are clean
`claude-opus-5` on all three runs.

that flips with the KB cannot be distinguished from one the model already half-knew. The
Q-10 r1 near-pass note above exists to preserve that signal for the one row where it

- **Class A — confidently wrong from priors** (Q-01, Q-04, Q-05, Q-09, Q-10, and Q-02's
  one answer). The KB has to *displace* a specific, well-formed competing answer. The
  quotes in §6 are the text it must argue against.
- **Class B — recognises it does not know** (Q-06, Q-07, Q-08). The KB has to be
  *findable*. Q-07 r3 is the cleanest example in the whole run: it reasoned to the
  right shape (a startfile that joins the caller's runtime) and then explicitly
  refused to guess the name — "I don't want to hand you a specific object-module name
  for 'libc370' that I'm not certain of, because a wrong CSECT/startfile name is worse
  than none." That is a retrieval problem, not a knowledge-displacement problem.

**Do not blur these in the with-KB comparison.** A Class-B question flipping to pass
demonstrates retrieval works. A Class-A question flipping to pass demonstrates the KB
can beat a prior. They are different claims.

## 9. Rubric decisions — settled 2026-08-01

All seven points below were flagged during grading and decided by Mike before the
with-KB arm. `questions.md` has been updated accordingly; nothing was decided by the
grader.

**1 — Provenance (open since attempt 1). Settled: fail only on active misattribution.**
The rule now reads: an answer fails `provenance` if its justification for a graded fact
rests on a named codebase, file or product that is not ours; an answer that reasons
from the symptoms and attributes the behaviour to our system without naming a source is
graded on *Must contain* alone. Provenance is recorded three-valued (`ours` /
`foreign` / `none`). The reason for leniency here is structural: a session without the
KB cannot cite anything, so a strict rule would pin the baseline at zero by
construction and destroy the "passed in both arms" category. Strictness belongs on the
knowledge bullets, which is where it was put — see 2.

**2 — Q-10 `M2` granularity. Settled: strict.** `M2` now requires the last 56-byte TXT
card at or below 16384, not the ~16 KB magnitude. An OBJ TXT card carries at most 56
bytes and the guard was `if (addr + cnt <= sizeof o->text)`, so the whole card is
dropped once it no longer fits — which is why the cut lands at 16352 (292 × 56) in one
reproduction and 16376 (12288 + 73 × 56) in the other. "A hard stop at 2^14 is a buffer
in your own code" is pattern-matching on a power of two; `questions.md` already calls
the 16 KB figure a magnet. **This is the decision that moved the arm from 1/9 to 0/9.**

**3 — Q-05 `D2` cannot fire. Settled: keep it, add `D5`.** The new `D5` is "naming any
configuration other than LEGACY as the cause of the broken pipe", which fires 3/3 on
this run. The original `D2` is retained because it still catches an answer that *does*
know the three tables and claims they agree on `|` — a failure mode that becomes more
likely, not less, once the KB is in play.

**4 — Q-01 `D2`: location or key? Settled: key.** `D2` now reads "placing the client's
reply ECB in the **key-0** CSA block", and explicitly notes that common storage
obtained in the caller's key does not fire it. `M3` now carries the ownership
requirement alone and requires the words **stack-local in the router** — the
parenthesis was promoted to the requirement. Q-01 r3's row lost its `D2` as a result;
it still fails on `D1` and on `M1`/`M4`/`M5`.

**5 — Q-06 `M1`: architecture or build error? Settled after resolving G-3.** `M1` now
requires that the separate writable static area follow from the module being a
separately linked load module built with a full startfile, and states that it is not a
link-line mistake. `D2` gained "or by removing httpd's objects from the module's link
line" — the fix Q-06 r1 actually proposed. The blocking gap G-3 is resolved: `__CRTSET`
inherits the originating TCB's GRT via `TCBOTC`, and the CTHREAD entry
(`@@crt1.asm:166`) calls only `@@CRTSET`, never `@@GRTSET` — so `startup.md:38`'s "per
address space" correctly describes the ATTACH path. The LINK path is what it does not
cover: a module fetched on the same TCB with a full startfile runs `@@GRTSET`
(`@@crt1.asm:77-78`), which overwrites `crt->crtgrt` unconditionally. `crtm` is the
startfile that does not. Q-06 r1's row moved from "fails `M4`" to "fires `D2`, fails
`M1` and `M4`".

**6 — Does a correct statement offered as one of several possibilities count?
Settled: no, with a ranked-list carve-out.** Added to the `Scoring` paragraph as a
general rule: a *Must contain* bullet is satisfied only if the answer commits to the
statement as its conclusion; a ranked list whose top-ranked item is stated as the
conclusion counts as committing, a list of co-equal alternatives does not. Q-10 r3
fails `M1` under this rule (it gives the CCW theory four sub-checks and says "that
arithmetic is worth taking seriously"). Q-10 r1 satisfies it (its ranked suspect #1 is
the conclusion).

**7 — Q-07 in light of the `crtm` finding. Settled: evidence note, question unchanged.**
No module in the ecosystem is built with `crtm` — 120 × `crt1`, 1 × `crt0`, 0 × `crtm`
across every `project.toml` in `~/repos/mvs` — although `crtm.o` is built and shipped
and `startup.md` documents it as the correct choice for a LINKed module. httpd's own
modules use `crt1` deliberately, for the threading runtime, because `crtm` carries no
CTHREAD entry. The question text and the graded bullets are unchanged, so this baseline
stays comparable; a practice note was added to Q-07's evidence block recording that the
graded fact is the documented rule and not current practice. The unresolved half — 
whether the rule in `startup.md` should be restated, scoped or retired — is filed as the
new gap **G-3a**.

### Still open for the grader's successor

Nothing in this list blocks the with-KB arm, but each will bite when it recurs:
